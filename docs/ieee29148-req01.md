# Especificación de requisito REQ-01 — Registro de agricultores

**Norma de referencia:** ISO/IEC/IEEE 29148:2018 (ingeniería de requisitos) · **Proyecto:** AgroValle Connect
**Historia de origen:** HU-01 (BACKLOG.md) · **Prioridad:** Must Have · **Puntos de historia:** 5 · **Versión:** 1.0

Este documento reescribe la HU-01 como una especificación formal prescriptiva y la compara con la especificación ágil
con BDD (Given-When-Then) que ya existe en el backlog.

## 1. Identificación y propósito

| Campo | Contenido |
|---|---|
| Identificador | REQ-01 |
| Título | Registro de agricultores |
| Origen | HU-01, escenarios 1 y 2 del `BACKLOG.md` |
| Partes interesadas | Agricultor del Valle del Cauca (usuario), Product Owner, equipo de desarrollo, docente evaluadora |
| Propósito | Permitir que un agricultor cree su cuenta para ofrecer sus productos directamente a compradores |
| Estado | Aprobado para el Sprint 1 |

## 2. Alcance y contexto de operación

El requisito cubre el alta de un agricultor mediante la API REST de AgroValle Connect: la recepción de sus datos, su
validación, su almacenamiento en PostgreSQL y la respuesta al cliente. Quedan fuera de este requisito el inicio de sesión
(REQ de HU-13), la gestión del perfil y el registro de compradores, que no tiene historia propia en el backlog.

Contexto: aplicación cliente web que consume la API bajo `/api/v1`, servidor Spring Boot en Java 17 y base de datos
PostgreSQL (`schema.sql`).

## 3. Definiciones

- **Agricultor:** persona productora que publica cosechas en la plataforma.
- **Municipio del Valle:** uno de los 42 municipios del catálogo `municipio`.
- **Cédula válida:** cadena de 6 a 10 dígitos numéricos.
- **Contraseña cifrada:** resultado de aplicar BCrypt a la contraseña; es lo único que se almacena.

## 4. Requisitos funcionales

Método de verificación: **P** = prueba automatizada, **I** = inspección del código o del esquema, **D** = demostración.

| ID | Cláusula normativa | Justificación | Verificación |
|---|---|---|---|
| REQ-01-F01 | El sistema deberá exponer el recurso `POST /api/v1/auth/register` para registrar agricultores. | Contrato REST inicial de HU-01. | P |
| REQ-01-F02 | El sistema deberá aceptar un cuerpo JSON con los campos `nombre`, `ubicacion_valle`, `cedula`, `correo` y `contrasena`. | El BDD exige nombre, ubicación y cédula; correo y contraseña son necesarios para el inicio de sesión de HU-13. | P |
| REQ-01-F03 | El sistema deberá rechazar la solicitud si `nombre` está vacío o supera 120 caracteres, o si `ubicacion_valle` está vacía. | Escenario 2: datos obligatorios incompletos o inválidos. | P |
| REQ-01-F04 | El sistema deberá rechazar la solicitud si `cedula` no está formada por 6 a 10 dígitos. | Escenario 1: "cédula válida". | P |
| REQ-01-F05 | El sistema deberá rechazar la solicitud si `correo` no tiene formato de correo electrónico o supera 150 caracteres. | Identifica de forma única al usuario. | P |
| REQ-01-F06 | El sistema deberá rechazar la solicitud si `contrasena` tiene menos de 8 o más de 72 caracteres. | 72 es el máximo que procesa BCrypt. | P |
| REQ-01-F07 | El sistema deberá verificar que `ubicacion_valle` corresponda, sin distinguir mayúsculas, a un municipio del catálogo del Valle del Cauca y rechazar la solicitud en caso contrario. | La plataforma atiende únicamente al Valle del Cauca. | P |
| REQ-01-F08 | El sistema deberá rechazar el registro si la cédula ya pertenece a otro agricultor. | Evita cuentas duplicadas de la misma persona. | P |
| REQ-01-F09 | El sistema deberá rechazar el registro si el correo ya pertenece a otro usuario. | El correo es el identificador de acceso. | P |
| REQ-01-F10 | El sistema deberá recortar los espacios sobrantes y almacenar el correo en minúsculas. | Evita duplicados por diferencias de formato. | P |
| REQ-01-F11 | El sistema deberá almacenar la contraseña únicamente cifrada con BCrypt. | Protección de credenciales. | P, I |
| REQ-01-F12 | El sistema deberá crear el usuario, su perfil de agricultor y la asignación del rol `AGRICULTOR` en una única transacción atómica. | Evita registros a medias. | P |
| REQ-01-F13 | El sistema deberá responder `201 Created` con el identificador, nombre, cédula, correo y `ubicacion_valle` del agricultor registrado. | Escenario 1. | P |
| REQ-01-F14 | El sistema deberá responder un error del cliente (`400 Bad Request`) con una descripción del problema, sin crear ningún registro, cuando los datos sean incompletos o inválidos. | Escenario 2. | P |
| REQ-01-F15 | El sistema no deberá incluir la contraseña ni su cifrado en ninguna respuesta ni en los registros de log. | Confidencialidad. | P, I |

**Pendiente con el Product Owner:** el código de respuesta ante cédula o correo duplicados. El diseño propone
`409 Conflict`; si se decidiera `400`, solo cambia el manejador de errores.

## 6. Interfaz externa

Solicitud:

```http
POST /api/v1/auth/register
Content-Type: application/json

{
  "nombre": "Pedro Perez",
  "ubicacion_valle": "Dagua",
  "cedula": "1130456789",
  "correo": "pedro@correo.com",
  "contrasena": "clave12345"
}
```

Respuesta exitosa (`201 Created`):

```json
{
  "id": 1,
  "nombre": "Pedro Perez",
  "cedula": "1130456789",
  "correo": "pedro@correo.com",
  "ubicacion_valle": "Dagua"
}
```

Respuesta de error (`400 Bad Request`, formato propuesto):

```json
{ "estado": 400, "error": "Datos inválidos", "detalles": ["cedula: debe tener entre 6 y 10 dígitos"] }
```

## 7. Supuestos y restricciones

- `correo` y `contrasena` no figuran en el BDD original, pero HU-13 los necesita; se incorporan al contrato.
- El registro de compradores no tiene historia propia; se asume que usa el mismo recurso con el rol `COMPRADOR`.
- El catálogo de municipios es fijo y se carga con `schema.sql`.

## 10. Comparativa: especificación IEEE 29148 frente a historia de usuario con BDD

| Criterio de ingeniería | Especificación formal IEEE 29148 (SyRS) | Historia de usuario ágil + BDD |
|---|---|---|
| Propósito y enfoque | Documentación prescriptiva, exhaustiva e inmutable para acuerdos contractuales. | Carta de conversación ágil, ejecutable y enfocada en el valor continuo del usuario. |
| Sintaxis y estructura | Cláusulas normativas estructuradas ("El sistema deberá proporcionar..."). | Formato "Como [Rol] quiero [Acción] para [Beneficio]" más escenarios Given-When-Then. |
| Validación y pruebas | Matriz de trazabilidad de requisitos y casos de prueba manuales. | Especificación ejecutable, traducible directamente a métodos `@Test` en JUnit 5. |
| Gestión del cambio | Requiere comités formales de control de cambios (CCB) y revisiones rígidas. | Refinamiento continuo (Backlog Grooming) adaptativo al inicio de cada Sprint, por el Product Owner. |

### Lo que se observó al reescribir HU-01

- **El BDD dejó implícitas varias reglas.** Los dos escenarios originales no dicen nada sobre cédulas o correos
  duplicados, el catálogo de municipios, el cifrado de la contraseña, los límites de cada campo ni el contenido de la
  respuesta. La reescritura formal obligó a explicitarlas: 15 cláusulas funcionales frente a 2 escenarios.
- **El BDD aportó rapidez y ejemplos ejecutables.** Cada escenario se convierte en una prueba con poco esfuerzo y deja
  claro el caso feliz y el error principal; la especificación formal, en cambio, es más larga de mantener.
- **Se complementan.** La especificación formal sirvió como lista de verificación para no olvidar reglas; los escenarios
  BDD siguen siendo las pruebas de aceptación. En un proyecto ágil como este conviene refinar con BDD cada Sprint y
  reservar la forma IEEE para los requisitos críticos o de seguridad, como el de este registro.
- **Costo del cambio.** Si el Product Owner decide que un duplicado responde `400` y no `409`, en el BDD basta editar un
  escenario; en la forma IEEE se actualiza además la cláusula, la matriz de trazabilidad y su aprobación.
